1 · The problem

Same model, same GPU, much faster, answers unchanged

A university library wants semantic search: a student types a question and gets the passages that match its meaning. Every passage is turned into an embedding, a list of 768 numbers, by the text encoder BAAI/bge-base-en-v1.5 (a 12-layer BERT, about 110 million parameters). The library has millions of passages and one modest GPU, and re-embedding the collection takes days.

The challenge: make the existing model run faster on the existing hardware. The rules are strict.

What is not allowed

  • A different or smaller model, or changed weights
  • INT8 or other quantisation, pruning, distillation
  • Approximate attention

What is allowed

  • FP16 or BF16 arithmetic
  • Batching and scheduling changes
  • Faster kernels, compilation

How it is scored

Tolerance gatecosine ≥ 0.999 to the FP32 reference on every input, or the run scores zero
Throughput, 50%log scale: 1× = 0, ~6× = half, 40× = full marks
Profiler report, 25%before/after evidence of where time went
Live latency, 15%p50 and p99 on a hidden query trace
Demo, 10%the working system

The judges run our single file team.py on their own GPU with 100,000 passages we have never seen and a different query trace, so nothing may be tuned to the practice data.

2 · Diagnosis

Why the reference is slow

The reference (reference.py) runs the model in FP32, pads every input to 512 tokens, and processes 32 inputs at a time. On the practice set the average passage has 100 tokens. Here are twelve real passages as the reference sees them: blue is real text, hatching is padding that is computed and then thrown away.

Measured with the model's tokenizer on all 100,000 passages (exact counts) and with torch.profiler on 2,000 passages. The core insight: the model is not the problem; the way it is run is.

4 · Kernel-level architecture

5 · Optimisations

Each optimisation, what it does, and what it was worth

Every idea can be switched on and off with an environment variable, so each was measured on its own with the official bench.py, end to end including tokenisation. Stages are cumulative.

Stages 1–4: one run each on 20,000 passages at token budget 65,536 with an FP32 residual stream (an earlier precision fix). At that budget the laptop GPU used ~90% of its memory and timings drifted by up to 34% between identical runs, so the final choices used three interleaved runs at small budgets (Section 6). Last row: the submitted file on all 100,000 passages.

6 · Precision

Getting the answers right: the 100,000-passage finding

One passage below cosine 0.999 scores the whole run zero, and the judges use 100,000 passages we cannot see. The official harness only checks the first 2,000 passages. On those, plain FP16 scored a worst case of 0.999663, comfortably above the line.

We did not stop there. We embedded all 100,000 practice passages with our own FP32 path (which matches the official reference to 1.0000000) and compared every one.

What we learned

  • Every FP16 result below 0.9999 was a passage of 23 tokens or fewer. Above 32 tokens the worst was 0.999992.
  • The worst passage, #31022 (16 tokens: “Transport in Gippsland (region) Shire of South Gippsland”), fails even when encoded on its own, so this is arithmetic, not a bug in batching.
  • Short texts build their [CLS] vector from few tokens, so the same small rounding error turns its direction further.

The fix: precision where it is needed

Inputs of 32 tokens or fewer run through an FP32 copy of the same weights, in their own batches. They are 33% of passages but only 5.5% of tokens, so the cost is about 3% of throughput.

Live queries are short too, so the 32-token CUDA Graph also runs in FP32: about 2 ms more per query, and no precision risk on the hidden trace.

7 · Profiler evidence

Before and after, on the same 2,000 passages

torch.profiler traced each configuration; GPU time is the sum of kernel and copy durations in the exported trace (open results_gpu/profiler/*/trace.json.gz in ui.perfetto.dev).

GEMM (matrix multiply)AttentionLayerNorm + element-wise
  • GPU time 69.7 s → 3.3 s (21×) for the same 2,000 passages.
  • Idle gaps over 100 µs: 136 → 7; the GPU is busy 99.7% of the span. The CPU now prepares batches in the background.
  • In the final profile 79% is GEMM: what remains is the model's own matrix maths. 16.5% of GPU time is FP32 GEMM on short inputs, the price of zero violations.

Stage 1 and 2 were profiled with the FP32 residual stream (since replaced), which is why LayerNorm + element-wise reaches 24–25% there.

  • Allowed precision only: FP16 and FP32. No INT8; BF16 tested and rejected.

Limits: numbers are for an RTX 3050 Laptop GPU; the judges' GPU will differ. The reference baseline is a 5,000-passage sample, valid because its cost per passage does not depend on the text. Live queries cannot be batched together because bench.py sends them one at a time.
